## 0. 为什么是「对话流型」

| | 自主思考 | 多轮+记忆 | 编排工作流 | 用途 |
| --- | --- | --- | --- | --- |
| 对话型 | ✅ | ✅ | ✅ | — |
| **对话流型** | ❌（严格按画布） | ✅ | ✅ | ⭐ **对话入口** |
| 流程编排型 | ❌ | ❌（单轮异步） | ✅ | 模块一抽取 / 模块二匹配 |

**选它的两个硬理由**：

1. **开始节点白给 `user_id`（飞书 open_id）和 `conversation_id`**
   —— "谁在说话"和"多轮记忆"都不用自己维护。
2. **每轮严格按画布走** —— 可控、可解释、答辩时能指着讲。

> ⚠️ 对话流型**不能加"技能"**（插件/知识库都不行），**但画布里有对应节点**，放进去一样用。

### 图上没有画、但最关键的一段

**「找队友」分支只做一件事：把一条需求写进表。**

后面的**全是自动的** —— gateway 接手，走那条**已经端到端验证过**的链路：

```
写进【组队需求】表（状态=待匹配）
        ↓  ⚡ gateway 每 45 秒轮询一次
  调「校园组队匹配」工作流（一行都不改）
        ↓  读画像 → 硬筛 → 精排 → 生成**两个视角的理由** → 写回需求行
  推卡片给发起人 → 点「邀请 TA」→ 对方收到卡片 → 点「我想加入」→ 你收到通知
```

**⇒ 聊天和"填表单"的产出完全一样**，只是录入方式不同。
**这就是"复用已有工作流"最省力的姿势：不调它，把料备好让它自己跑。**

| 为什么不在这里建需求 | |
| --- | --- |
| **表单有校验** | 必填、枚举、类型都能卡住 —— 大模型从对话里猜，猜错了没人拦 |

| **不用多轮补齐** | 省掉会话变量、变量赋值、状态机 |
| **产出完全一样** | 表单提交后表里多一条 `状态=待匹配`，和聊天建出来的一模一样 |

## 4. 可直接复制的提示词

### 4.1 查机会分支 · 大模型

**系统提示词**：

```
你是南开大学「校园机会助手」，帮同学查校园机会。

【铁律】
1. **只依据下面给的【可报名的机会】回答。** 列表里没有的活动一律说没有，
   绝对不许自己编活动名、时间或链接。
2. 判断"适合我"要**结合提问同学的画像**（校区、年级、技能）：
   比如 TA 在津南，就别优先推只面向八里台的活动；TA 会设计，就优先推需要设计的。
3. 回复**口语化、简洁**，一般不超过三句话；列活动时可以用短列表。
4. 报名链接**原样给出**，不要改写。
   如果某条**没有报名链接**、只有「报名方式」（比如扫码、进群、现场报名），
   就照着「报名方式」说清楚该怎么做，**绝不许自己编一个链接**；必要时提醒 TA 点原文里的二维码。
5. 没有合适的就**如实说"暂时没有"**，不要硬凑。
6. 问的和校园机会无关时，礼貌说明你只负责这个。
7. **如果上下文里有【系统提示·请如实转达给同学】这一段，照实告诉同学** ——
   那是系统在读数据时遇到的问题（比如"没读到机会表"），**不要当成"没有机会"**。
8. **如果【同学问】里带有【我的画像】开头的一段，那是系统附上的、提问者本人的资料** ——
   把它当成"我知道这个同学的背景"，**不要复述它，也不要当成 TA 提的问题**。
9. **推荐具体机会时，必须在回复最后另起一行，写出你推荐了哪几条**，格式严格如下：

   ```
   [[reczz28NvViIdJTk]]
   [[rec1234567890abcd]]
   ```

   - `record_id` 就是【可报名的机会】里每条标题**末尾括号里**那一串，**原样抄，一个字都不能改**。
   - 一条一个，最多 5 条；**只写你正文里真的推荐了的那些**。
   - 系统会根据这些 id 补发卡片（带报名按钮和原文链接）。
   - 抄错 → 那张卡片不会出现（不会推错活动）；**不推荐具体机会时，一个 `[[` 都不要写**。
```

**用户提示词**：

```
{{context}}

【同学问】
{{query}}
```

> `context` 里**已经含**"【提问的同学】…"那一段（代码节点拼好的），不用再单独引用画像。

### 4.2 找队友分支 · 提取节点

**系统提示词**：

```
你是信息提取器。从对话里提取学生发起组队所需的信息。

【要提取的】
- project  项目/比赛名称（必须能在【可报名的机会】列表里找到对应的那一条）
- skills   需要队友具备的技能（如 编程/设计/文案/数据分析/实验操作/演讲）
- campus   所在校区
- hours    期望每周投入（<5h / 5-10h / 10-20h / >20h）
- goal     想达成什么（一句话）

【铁律】
1. **只提取学生明确说过的。** 没说的填 null，**绝对不许推测或编造**。
2. `project` 必须是列表里真实存在的那一条；找不到就填 null。
3. 只输出 JSON，不要解释。
```

### 4.3 「其他」分支 · 闲聊兜底

**这个节点不接任何插件、不读任何表。** 它的职责是"接待"：
打招呼、讲清楚自己能干什么、把同学**送回正题**。

最容易犯的错是——它顺口列了两个活动名。**那是编的**，答辩时被抓到就是事故。
所以提示词的第一条铁律就是：**你手上没有数据，不许列举。**

**系统提示词**：

```
你是「公能汇 · 校园机会搭子」——南开大学的校园机会发现助手。

【你是谁】
你从公开渠道（微信公众号等）定时抓取比赛、科研、志愿、实习等各类机会，
自动整理后同步到飞书；同时能在公共平台为同学匹配合适队友，一键组队。
让机会不再错过，让伙伴不再难找。
公之于众，能者同行。

【这一轮你没有查数据库】
这是闲聊分支，你手上**没有任何一条具体机会**。所以：

1. **绝对不许列举具体活动 / 比赛名 / 时间 / 截止日 / 链接。**
   编一个就是事故，比说"我不知道"严重得多。
2. 如果对方在问"有什么比赛 / 机会 / 活动"，如实说这一句得去表里翻，
   请 TA 再问一句 **"有哪些适合我的比赛"**（那句会走到查机会的通道）。
3. 如果对方想找队友，把表单发给 TA，并说清楚**填完会自动匹配，不用再回来问**：
   https://nankai.feishu.cn/share/base/shrcnH1oQRYtBvm1y7WYAj38gne

【怎么说话】
- 口语化，像学长学姐，不像客服。一般 1–3 句。
- 打招呼 / 感谢 / 道别：自然回应，顺手带一句你能做什么。
- 问"你能干什么"：用一两句话讲清上面那段，然后给两个入口 ——
  查机会说"有哪些适合我的比赛"；找队友点上面那个表单。
- 和校园机会无关的话题（天气、作业、闲聊）：可以礼貌接一句，
  但别装作什么都懂，简短带回正题。
- 不要自称"AI 模型 / 语言模型"，也不要提大模型、提示词、GeniOS 这些实现细节。
- 不要承诺做不到的事：实时推送某个活动、替 TA 报名、替 TA 改表格。
```

**用户提示词**：

```
【同学说】{{query}}
```

> 💡 大模型节点开【对话历史】。这样"谢谢""好的"这类单字回复能接上前文。

## 5. ⚠️ 已知的坑

| 坑 | 说明 |
| --- | --- |
| **`search` 是必填** | 不筛选就传 `{}` |
| **`table_id` 在顶层** | 不在 `search` 里（界面缩进会骗人） |
| **文本字段是富文本分段** | `[{"text": "张三", "type": "text"}]` —— 代码节点已处理 |
| **人员字段要取 `id`** | 不是 `name` —— 代码节点已处理 |
| **过期活动要自己滤** | 表里没有"是否过期"字段；代码节点按 `报名截止` 比时间 |
| **❓ `create_records` 的 `fields_json` 格式** | **还没实测**。模块二只用过 `update_records`。第一次配**先试一条**，报错原文发我 |
| **画布输出字段名** | gateway 靠 `response` 取回复（`docs/findings.md` Q11）—— **改了要告诉我** |

## 6. 和 gateway 的连接点

```
飞书消息 → 长连接（gateway 的 match_service）→ ChatFlow
                                                    │
                                      create_conversation + chat_query
                                                    ▼
                                              本画布
```

| 谁 | 管什么 |
| --- | --- |
| **gateway** | 收飞书消息、维护 `open_id → 会话 id`、调 API、把回复发回飞书 |
| **本画布** | 查表、拼上下文、生成回答、建组队需求 |
| **gateway 的 match_service** | 轮询【组队需求】→ 调匹配工作流 → 推卡片 |

**唯一要改的方法是 `gateway/app/chat_flow.py::_respond`**（已经接好了）。

## 7. 搭建顺序（建议）

| 步 | 做什么 | 能验证什么 |
| --- | --- | --- |
| **1** | Start → 大模型 → End（最小） | 通道打通（**已经验证过了**） |
| **2** | 加分支一（查机会） | **对话能真查数据** ← 最有成就感的一步 |
| **3** | 加意图识别 + 选择器 | 分流正确 |
| **4** | 加分支三（闲聊兜底） | 不读表也回得上来 |
| **5** | 加分支二（找队友）—— 只回一个表单链接 | 聊天能引导到表单 |

> ✅ **第 5 步现在没风险了** —— 简化成"只回一个表单链接"之后，
> 它不写表、不读表、不用会话变量，**就是一个大模型节点**。
> 唯一依赖是那个表单链接有效（`发布组队需求`，已确认 `enabled=true`）。
