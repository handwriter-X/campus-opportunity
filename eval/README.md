# eval/ —— 评测集

阶段 5 用。目标：让「抽取准不准」变成一个**可复现的数字**，而不是感觉。

## 目录

```
eval/
├─ samples/         真实公众号文章（以及探针 S3 抓到的原始 Webhook 载荷）
├─ labels/          人工标注（每条对应一个 sample）
└─ run_eval.py      比对抽取结果与标注，输出指标（待写）
```

## samples/ 怎么攒

两条来源，都不需要你手动复制粘贴：

1. **探针 S3 的落盘**：`/ingest/_debug` 每收到一次载荷就写一份到
   `data/captures/ingest_debug_*.json`。挑有代表性的拷进 `samples/`。
2. **backfill 回放**：`ENABLE_PUSH_AFTER` 之后的文章会标 `mode=backfill` ——
   它们照常送工作流抽取，但**不推送**。这正是为了攒评测样本（方案阶段 1、阶段 5）。

目标 **50–100 篇**，并且要**故意凑齐这几类**，否则指标会好看但没意义：

- [ ] 纯非机会文章（新闻、通知、喜报）—— 测**非机会误判率**
- [ ] 含多个机会的汇总推文 —— 测**拆分能力**（验收清单第 3 条）
- [ ] 同一活动被两个公众号转发的两篇 —— 测**去重**（第 4 条）
- [ ] 时间表达含糊的（「本周五」「下周三」）—— 测**相对日期解析**
- [ ] 关键字段缺失的（没写名额、没写地点）—— 测**不编造**（第 6 条）
- [ ] 四类机会各若干 —— 测**分类准确率**

## labels/ 怎么标

每篇一个 `labels/<sample 名>.json`，按 `genios/schemas/opportunity.schema.json` 的结构标。

⚠️ **samples 和 labels 两个目录现在都是空的**，原因见 `genios/README.md`：
标注要用字段体系文档定义的口径，文档没到位就标不了。

## run_eval.py 输出什么（阶段 5）

- **字段级准确率**：逐字段比对（机会名称、类型、报名截止时间、地点…）
- **依据校验通过率**：关键字段的原文引用是否真的出现在原文里
- **非机会误判率**：把非机会文章判成机会的比例
- **拆分召回率**：多机会汇总推文里，被正确拆出来的比例

⚠️ 时间类字段要比对**规范化后的 ISO 时间**，但报告里要同时显示原文时间表达 ——
否则一旦是相对日期解析错了，你看不出错在哪一步。
